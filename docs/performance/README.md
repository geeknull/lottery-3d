# CSS3D 舞台性能实测

本轮最明确的改进是消除同帧重复绘制：三个名单规模、共九轮升级后采样的 `renderer.render` 每帧最多调用一次，基线各规模均观察到最高四次。帧间隔整体改善，但 3000 人仍明显卡顿，1000 人仍需在实际投影电脑上彩排。500 人的基线第一轮比升级后更快，不能把本轮结果表述为所有场景都提速。

原始记录：[基线 9422214](baseline-9422214.json)、[本轮升级版本 506e6e4](upgraded.json)。采样程序：[benchmark-stage.mjs](../../scripts/benchmark-stage.mjs)。基线采于 2026-09-30 20:14:54，最终升级版采于 20:54:30，均为北京时间。

## 环境与采样方法

两次记录的环境一致：Apple M4 Pro、arm64、Darwin 25.6.0，Playwright Chromium 148.0.7778.96，headless 模式，1440 × 900 视口，访问 `http://127.0.0.1:18182` 的 Vite 开发服务。机器后台负载未严格控制；本报告仅比较一次基线采样与一次最终版本采样，没有固定版本的交替复测或多批次重复，因此不能据此给出稳定加速比例，也不能把开发环境的无头浏览器数据当成现场 FPS 保证。

每个规模使用新的浏览器 context 和相同规则生成的 500 / 1000 / 3000 人名单，头像使用 `initials` 并开启大名单自动降级；关闭音频、倒计时，设置一个共 30 人、每轮抽 10 人的测试奖项。每个名单连续执行三轮抽奖，不在轮次之间刷新页面。

- **初始化**：导航后等待 `STATUS.isWait()`，读取页面 `performance.now()`。这是脚本的启动观测值，包含页面加载和等待开销，并非独立测量的场景构造耗时；脚本没有另外检查所有初始动画都已完成。
- **帧间隔**：进入旋转状态后，通过独立 `requestAnimationFrame` 回调采样至少四秒，丢弃首个间隔，再排序取 `floor(样本数 × 0.95)` 位置的值作为 p95。卡顿会令实际窗口超过四秒。这里测的是旋转期的 rAF 间隔，未覆盖完整减速、飞卡或分组镜头的性能。
- **绘制次数**：在同一采样窗口包裹 `renderer.render`，按采样 rAF 回调递增的帧编号统计每帧调用数。它统计应用渲染调用，不能代替 GPU 绘制、合成或屏幕实际呈现帧数。
- **内存**：初始化后、每轮揭晓完成后，分别经 CDP 强制 GC，再读取 `JSHeapUsedSize`。JSON 字段名为 `heapMB`，实际计算除以 `1024²`，下表因此标为 MiB；不包含完整浏览器进程、GPU 或全部原生 DOM 内存。

## 前后数据

时间均为毫秒；p95 范围是三轮各自 p95 的最小值至最大值，**不是合并样本计算的 p95，也不是置信区间**。逐轮原值保存在上面的 JSON 中。

| 人数 | 版本 | 初始化 | 三轮 p95 范围 | 各轮间隔样本数 | 各轮每帧最大 render 调用 |
| ---: | --- | ---: | ---: | --- | --- |
| 500 | 基线 | 841.2 | 16.8–124.8 | 409 / 54 / 68 | 4 / 2 / 4 |
| 500 | 升级后 | 878.7 | 41.7–41.8 | 194 / 189 / 187 | 1 / 1 / 1 |
| 1000 | 基线 | 2827.9 | 258.0–309.5 | 16 / 18 / 19 | 2 / 4 / 3 |
| 1000 | 升级后 | 1385.1 | 66.9–75.1 | 73 / 77 / 80 | 1 / 1 / 1 |
| 3000 | 基线 | 6555.5 | 3144.7–4108.2 | 5 / 2 / 2 | 4 / 4 / 4 |
| 3000 | 升级后 | 4879.9 | 574.8–600.1 | 12 / 10 / 10 | 1 / 1 / 1 |

3000 人基线每轮仅有 **2–5 个间隔样本**，此时脚本的 p95 就是该轮最大观测值，统计很不稳定。升级后每轮也只有 10–12 个样本，仍不适合对外宣称精确的提升倍数。其升级后三轮中位帧间隔仍为 558.3 / 574.8 / 557.6 ms，足以说明这台机器的本轮无头采样中旋转持续卡顿。

500 人升级后的三轮 p95 更接近，但初始化观测值从 841.2 ms 增至 878.7 ms，且基线第一轮 p95 为 16.8 ms。因此这里只报告实测分布，不宣称初始化或每一轮动画都变快。

## 实现与现场取舍

单帧绘制去重是可以从执行路径和单测验证的确定性改进：动画、相机和控件更新只标记需要绘制，帧循环在这些更新完成后统一调用渲染器。九轮升级后采样均观察到每帧最多一次调用，与这一机制一致。布局变换同时从每卡两条 Tween 改为单一进度驱动；背面卡片不再显示反字，500 人及以上的非本轮赢家去掉卡片与文字阴影，全部参与者仍保留在场景中。

这些调整和演出节奏同时发生，本次没有做逐项 A/B 实验，不能将全部帧间隔差异归因于某一个优化。CSS3D 的大量 DOM 节点及浏览器合成成本依然存在；去重不等于保证流畅。

本轮继续使用 CSS3D，保留可读姓名卡与现有离线、双屏和视角控制。背景使用 140 个轻量 Canvas 粒子与静态 CSS 光环，未增加 WebGL 层；定格时背景静止。当前数据不能支持继续叠加高成本背景动效：3000 人需要进一步降耗或专门渲染方案验证；1000 人应先用最终名单、头像、主题、真实双屏与投影分辨率彩排，再判断现场节奏。需要时可使用系统“减少动态效果”及跳过演出，固定结果仍可用总览和分组近景展示。

## 复现

以下命令应在仓库根目录执行。先确认目标端口归属，使用自己启动的预览服务；不要复用未知服务或结束未知进程。核心 E2E 独占 18180，PWA E2E 独占 18181，性能采样另用 18182 或空闲端口，避免与浏览器验收并行争抢资源。

```sh
pnpm install --frozen-lockfile
pnpm dev --host 127.0.0.1 --port 18182 --strictPort
```

另开终端，在确认预览服务是要采样的版本后运行：

```sh
BENCH_URL=http://127.0.0.1:18182 node scripts/benchmark-stage.mjs repeat-upgraded
```

脚本会启动自己的无头 Chromium，依次采样三个名单，并写入 `docs/performance/repeat-upgraded.json`。如环境缺少 Playwright Chromium，先执行 `pnpm exec playwright install chromium`。每次使用新的标签，保留原始记录；复现本报告时不要覆盖已提交的两个 JSON。

基线必须在单独准备的 `9422214` 检出目录中启动相应服务。若该提交尚无采样脚本，将本报告链接的同一份脚本复制到该目录的 `scripts/benchmark-stage.mjs`，使用该目录已安装的依赖执行，并指定独立输出标签。不要在运行中的预览目录来回切换版本。公平比较还应固定浏览器版本、窗口尺寸与设备供电，记录后台负载，重复多批次并交替版本；最后用生产构建和现场设备补测。

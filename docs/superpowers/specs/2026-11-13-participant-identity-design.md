# 参与者身份列（工号、部门）设计文档

日期：2026-11-13

本文只做设计，不改生产代码。结论经过一次性原型验证（原型已删除，规则和结果见“原型结论”）。

## 目标

1. 名单可以带可选的“工号”和“部门”两列，解决重名无法区分的问题：两个张伟中一个中奖，导出文件和现场展示都能看出是哪一位。
2. 没有身份列的名单，行为、卡片 ID、配置指纹、验证文件和导出文件逐字节不变。
3. 旧存档、旧配置文件、旧验证文件都能照常读取和验证。

## 非目标

- 不做按部门分组显示、部门统计报表。名单顺序是公平算法的输入，任何分组展示都不能改变抽奖用的名单顺序。
- 不做按部门限定奖池、按部门配额。
- 不支持带双引号的标准 CSV 单元格（含逗号的部门名）。现有解析器也不支持，见待决问题 3。
- 不改随机算法、抽奖流程、`phase` 状态。

## 原型结论

原型文件 `src/views/lottery/core/roster-identity.spike.test.ts` 已运行，19 个用例全部通过，随后删除，没有提交。

- **旧格式不变**：9 种旧输入（纯名字、`名字,链接`、Excel 制表符 `张三\t研发部`、`张三,研发部`、全角逗号加 data URL、前后空白和空行、首行恰好是“姓名”、首行是 `姓名,职级`、带 BOM）用新解析函数得到的结果和现在的 `parseRosterEntries` 做 `toEqual` 完全一致，并且结果里没有 `employeeId`、`department` 键。做法是：首行不是“姓名 + 至少一个已知列名”时，直接调用现有解析函数。
- **新格式**：`姓名,工号,部门`、制表符粘贴、全角逗号、BOM、未知列被忽略、行比表头短、头像列放最后且 data URL 含逗号，都能正确解析。
- **往返**：有身份列的名单用 `rosterEntriesToText` 的新写法输出（带表头），再解析得到相同数据；没有身份列的名单输出和现在完全相同。
- **ID**：`buildCards` 对两个张伟仍给出 `张伟`、`张伟-2`，与有无身份列无关。
- **指纹**：没有工号的名单，新指纹函数结果和现有 `configHash` 相同，只加部门也相同；有工号时，改部门指纹不变，两个同名者互换工号指纹会变。现有只含名字的指纹检测不到这种互换（原型里两种顺序的哈希相等）。
- 原型没有找到任何会让旧名单解析结果变化的新格式写法，所以不触发 STOP 条件。

## 设计

### 1. 输入格式

**推荐：表头行触发。** 粘贴或 CSV 的第一个非空行，如果第一格是 `姓名`（也认 `名字`、`name`，不分大小写），并且后面至少有一格是已知列名（`工号`、`编号`、`部门`、`头像`），整段按表头模式解析：

- 列按表头对应，顺序随意；`工号`、`编号` 都映射为工号；不认识的列忽略。
- 行比表头短时，缺的列按空处理；空工号、空部门不写入。
- 头像列必须是最后一列，它之后的整段原样保留，因为 data URL 本身含逗号。头像值仍要通过现有 `AVATAR_PATTERN`，否则丢弃。
- 分隔符沿用现在的 `,`、Tab、`，`，BOM 在解析前去掉。

没有这样的表头时，直接走现有 `parseRosterEntries`，行为完全不变。

放弃的方案：
- **无表头，按列位置约定（第二列工号、第三列部门）**：会把现有 `张三,研发部` 的第二列当成工号，改变旧名单的解析结果，违反非目标 2，原型对应的旧格式用例会失败。
- **新增专用语法如 `张三|A001|研发部`**：Excel 复制粘贴出来的是制表符，用户得手工改格式，不如表头直观，也要另学一套规则。
- **用面板上的开关告诉解析器“第二列是工号”**：旧名单打开开关后同样改变解析结果，而且开关状态要进配置，增加一个与名单文本分离的状态。

已知代价：没有表头的 Excel 两列粘贴（姓名、部门）仍然丢掉部门。面板在检测到“多列但没有已知表头”时给一行黄字提示：“检测到多列内容但没有表头，附加列被忽略；首行加上 `姓名,部门` 可启用”，不阻止保存。这个提示是正式实现的一部分，不是解析行为的改变。

### 2. 身份字段

**推荐：拆成两个可选字段，`employeeId`（工号）和 `department`（部门），都不必填。** 工号用来区分同名的人，进指纹；部门用来领奖核对和现场展示，不进指纹。

放弃的方案：
- **只要一个通用“编号”**：工号和部门语义不同（一个唯一、一个重复），合成一列后无法做“按部门汇总”，也没法决定哪个进指纹。
- **工号必填**：很多活动只有姓名，强制必填会拒绝合法的旧名单。

重复工号：面板显示黄字警告“工号 X 重复 N 处”，**不阻止保存**，因为卡片 ID 不依赖工号（见第 3 问），重复不会破坏抽奖和存档。是否改成阻止保存，见待决问题 2。

### 3. ID 规则

**推荐：卡片 ID 保持由名字生成（`createIdAllocator`，张三、张三-2），不用工号。** 工号只是卡片和导出里的展示与核对字段。

理由：
- 进度（`config-restore.ts:44`）、流水（`winnerIds`）、验证文件都按 ID 保存。已有名单加上工号列后，如果 ID 改成工号，指纹（名字）没变，旧进度的 ID 全部对不上，进度被当成无效拒绝（计划 007 虽会留底，但这一场抽奖仍然丢了）。
- 工号重复、含特殊字符、纯数字等情况都要另外处理，而名字生成的规则已经有测试覆盖。
- 无工号名单必须保持现有 ID，这是硬约束。

放弃的方案：**有工号时直接用工号当 ID**。唯一的好处是 ID 更稳定、卡片 `.details` 可以直接显示，但上面三条代价更大。卡片上显示工号改由展示层单独处理（第 6 问）。

### 4. 配置指纹

**推荐：工号进指纹，部门不进；而且没有工号时指纹和现在逐字符相同。**

具体做法：只有当名单里至少有一个工号时，才在哈希输入里增加一项 `rosterEmployeeIds`（与名单同序的数组，缺省用空串）；没有工号时哈希输入与现在完全一致。`configHash` 的三处调用（`lottery-config.ts:70`、`config-apply.ts:69/89/93`）要从传名字数组改成传带 `employeeId` 的条目，这是正式实现里需要小心的地方。

理由：进度按 ID 保存，ID 来自名字和序号。两个同名者（张伟、张伟-2）如果有人把两行的工号互换，名字不变、指纹不变，“张伟”这个中奖结果就悄悄指向了另一个人。原型验证了只含名字的指纹检测不到这种互换，含工号则能检测到。部门只是展示信息，修改它不应清空进度，和现在“头像、奖品图、揭晓节奏不进指纹”的原则一致。

放弃的方案：
- **身份字段都不进指纹**：实现最简单，但留下上面这个静默指错人的漏洞。
- **工号和部门都进指纹**：现场发现某人部门写错、改一下就要清空进度，代价过高，而部门不影响“谁是谁”。

代价：活动进行中修正工号笔误会触发“清空进度”的确认框。待决问题 1 请维护者确认能否接受。

### 5. 公平验证

**推荐：验证文件的名单条目增加可选的 `employeeId`，不加部门；`version` 不变（仍是 1，如果 008 已合入则保持它自己的版本）。**

- 验证文件名单变为 `{ id, name, employeeId? }[]`。没有工号时导出内容与现在完全一致。`lottery-fairness.ts:66` 只在有工号时才写这个键。
- 校验器（`fairness-package.ts:64-65`）对名单条目的检查是 `id`、`name` 为字符串，多出的可选字段不影响旧校验逻辑；新校验器接受缺失。所以旧验证文件继续有效，新文件也能被只看 `id`、`name` 的旧版本打开。校验器要额外检查：如果有 `employeeId`，必须是字符串。
- 部门不放进验证文件：验证文件会交给外部人员复核，部门对复核没有用，而且属于更敏感的信息。

**承诺上下文**（只和计划 008 有关）：

- 若 008 先合入：`commitmentContext` 在名单条目有工号时，把条目从 `[id, name]` 改为 `[id, name, employeeId]`，没有工号时与 008 约定的格式完全相同，旧承诺因此仍可复算。口径与配置指纹一致，只含工号，不含部门，图片、头像也不含。
- 若本设计先落地：008 的实现要把 `commitmentContext` 的条目格式留成可扩展的数组，并在 008 的测试里加一条“没有工号时上下文不变”。

放弃的方案：
- **不把身份放进承诺**：和指纹同样的互换问题——承诺只绑定 ID 和名字，赛后无法证明“A001 当时就是第一个张伟”。
- **身份（含部门）全部放进验证文件和承诺**：扩大了对外泄露面，也让改部门影响承诺，与第 4 问不一致。
- **验证文件升到 version 2**：旧版本应用会直接拒绝新文件，而加可选字段不会，没有必要升版本。

### 6. 展示与导出

**推荐：**

| 位置 | 内容 |
|---|---|
| 卡片 `.details`（`3d-card-element.ts:31-35`） | 有工号显示工号，否则显示 `card.id`（与现在相同）；仍用 `textContent`。部门放进 `title` 悬停提示 |
| 本轮揭晓名单（`LotteryControl.tsx:91`）、中奖横幅 | 只在名单里这个名字重名时，显示成 `姓名（工号）`，没有工号时用部门；不重名的人只显示姓名 |
| 喜报图（`poster.ts:94`） | 同上，只对重名者加括号后缀，避免网格里的单元格被撑宽 |
| 中奖名单 CSV（`buildWinnersCsv`） | 名单里有任何工号或部门时，表头变为 `奖项,姓名,工号,部门`，没有时保持 `奖项,姓名`，BOM 不变 |
| 抽奖流水 CSV（`historyToCsv`） | 有身份信息时在末尾追加 `工号,部门` 两列（`时间,操作,奖项,姓名,备注,工号,部门`），不插到中间，已有的按列取数脚本不受影响；没有时保持原样 |

流水里只存名字和 ID，不存工号。导出时按 `winnerIds` 在当前卡片里查身份，所以 `historyToCsv` 要增加一个可选的“按 ID 查身份”参数，不改 `DrawLogEntry` 的存档格式。所有新增单元格都要经过 `escapeCsvCell`（工号以 `=` 或 `+` 开头也会被中和）。

放弃的方案：
- **所有人的名字后面都跟括号身份**：卡片墙和喜报单元格会变挤，对不重名的人是噪音。
- **把工号写进 `DrawLogEntry`（新增 `winnerEmployeeIds`）**：要改存档格式并同步改 `config-restore.ts` 的校验，却只为了导出，查表即可。
- **CSV 总是输出 `工号,部门` 列**：没有身份列的活动会得到两列空列，并且打破现有对 CSV 的断言。

### 7. 兼容

**推荐：配置 `version` 保持 1，不升到 2。**

- `RosterEntry`、`Person`、`Card` 新增的都是可选字段。`isValidConfig` 对名单对象只检查 `name`、`avatar`，所以旧版本应用打开带身份列的新配置文件仍然成功，只是静默忽略身份信息；新版本读旧配置，字段缺省即可。
- `config-apply.ts:41` 的 `entry.avatar ? entry : entry.name` 要改成“有头像、工号或部门任一项时保留对象”，否则身份在保存时被丢掉。`isValidConfig` 要补上 `employeeId`、`department` 缺省或为字符串的检查。
- 旧进度：因为没有工号的指纹不变、ID 不变，已有存档照常恢复。已有名单加工号会改变指纹，按第 4 问的规则触发一次“清空进度”确认，这是预期行为。
- 旧验证文件：没有 `employeeId` 键，校验路径完全不变。

放弃的方案：**升到 version 2**。会让旧版本应用直接拒绝新配置文件，而新增的只是可选字段；另外要写一次 v1 到 v2 的迁移，没有收益。代价是旧版本应用重新导出配置时会丢掉身份信息，这是只在“新旧版本混用”时才会遇到的问题，写进待决问题 4。

## 正式实现的拆分建议

每个提交都带自己的测试，改动 UI 或流程的提交在 push 前跑 `pnpm e2e`。

7. `feat: 配置面板提示身份列用法`：改面板提示文案、重复工号警告、多列无表头提示、重名提示的措辞。验证：e2e 加一次手动查看。

## 留给维护者决定的问题

1. 活动进行中修正工号笔误会触发“清空进度”确认（工号进指纹的代价）。能接受吗？如果不能，可以退一步：只有名单里存在“同名”时，才把同名者的工号放进指纹，不同名者的工号随便改。

# 开抽前公证卡与随机状态升级 设计文档

日期：2026-11-13

本文只做设计，不改生产代码，不安装依赖。基线 `c3f9290`（计划 008 加盐承诺已合入）。公证卡和随机状态升级是两条独立的实现路线，可以分开立项、分开评审、分开合并。

## 目标

1. 把“开抽前记录并公布承诺指纹”这一步做成一张能投屏、拍照、打印的公证卡，主持人不用再手工抄 64 位十六进制。
2. 说清楚 32 位随机状态的实际风险，给出升级方案和兼容办法，让维护者决定要不要做。
3. 全程离线可用：不依赖在线随机信标、在线时间戳服务、外链图片。

## 非目标

- 不证明“指纹是什么时候公布的”。本地程序做不到，面板里“本地验证无法证明公布时间”那句提醒必须保留，公证卡上也要写。
- 不做在线时间戳、区块链存证、数字签名。
- 不改抽奖流程和 `phase` 状态。不改名单顺序、不改旧验证文件的验证逻辑。
- 本文不写可运行的攻击代码，风险只给量级。

## 一、公证卡

### 1. 卡片内容

**推荐：**

| 项 | 内容 |
|---|---|
| 标题 | 活动标题（`headerTitle`）+ “开抽前公证卡” |
| 指纹 | 64 位十六进制，每 8 位一组、两行各 4 组，组间留空；另给“短码”（前 8 位）方便口头念和聊天里核对 |
| 名单 | “名单 N 人”，只写人数，不列姓名、工号、部门 |
| 奖项摘要 | 每个奖项一行：`奖项名 × 名额（每轮 k 人）`，数据来自 `currentPrizes()` |
| 绑定范围 | 一句话：“指纹绑定本场名单顺序（姓名；若有工号则含工号）和奖项规则；修改名单或奖项会生成新指纹，需要重新公布” |
| 算法 | `SHA-256（含随机盐）`，以及随机算法标识（现在是 `mulberry32-v1`，升级后读 `algorithm`） |
| 生成时间 | 本机时钟，标注“本机时间，不能作为公布时间的证明” |
| 核对方法 | 三行：开抽后向主持人要“验证文件”；在面板点“验证文件”导入；面板显示的指纹应与本卡一致 |

不放：种子、盐、姓名。种子和盐一旦出现在卡片上，卡片就等于公布了全部结果。姓名和工号属于名单内容，卡片是公开物，只放人数。

按指纹状态区分三种卡片，不能一视同仁：

- **加盐 SHA-256（`seedSalt` 非空且指纹 64 位）**：正常卡。
- **旧存档无盐 SHA-256**：卡片显示醒目标签“仅绑定种子，不绑定名单和奖项规则”。
- **8 位 FNV-1a（非安全上下文）**：不生成卡片，按钮置灰并说明“此环境只有非加密的 8 位指纹，请用 HTTPS 或 localhost 打开”。

彩排模式（`?mode=rehearsal`）生成的卡片加水印“彩排，不具效力”，避免彩排卡被误当成正式凭证。

放弃的方案：
- **卡片列出全部姓名**：几百人放不下，工号和姓名公开还有隐私问题，而且名单本来就不是靠卡片传递的。
- **指纹只显示一整串**：现在的做法，人工核对时容易串行；8 位一组才方便逐组对读。
- **8 位 FNV 指纹也出卡**：非加密指纹做“公证”会给人错误的安全感。

### 2. 形式

**推荐：三种形式共用同一份卡片数据，第一版不做二维码。**

1. **投屏全屏卡片**：面板里加“公证卡”按钮，打开全屏浮层，深色底、大字号，直接用 React 文本渲染（不用 `innerHTML`）。
2. **PNG 下载**：复用 `poster.ts` 的思路，canvas 只画文字，不画外链图，不会被污染；文件名带短码，例如 `公证卡-1a2b3c4d.png`。
3. **打印**：给浮层加 `@media print` 样式，隐藏面板其他元素，黑字白底。

二维码：**第一版不做**。理由：卡片上要传递的只有 64 位指纹，二维码不能证明任何东西；扫码读出来还得再和验证面板人工比对，不如直接用下面第 4 问的“指纹核对输入框”；二维码要加依赖。

如果维护者以后想要，推荐 `uqr`，放弃 `qrcode-generator`。下面是 2026-11-13 在本机查到的数据：

| 库 | 版本 | 许可证 | 解包体积 | 未压缩 ESM 入口 gzip 后 | 依赖 | 最近更新 |
|---|---|---|---|---|---|---|
| `uqr` | 0.1.3 | MIT | 79,278 字节 | 7,804 字节（`dist/index.mjs`） | 无 | 2026-04-03 |
| `qrcode-generator` | 2.0.4 | MIT | 555,539 字节 | 11,100 字节（`dist/qrcode.mjs`） | 无 | 2025-08-07 |

放弃的方案：
- **只做 PNG，不做全屏**：现场要投屏时还得先下载再打开图片，慢。
- **只做打印样式**：很多现场没有打印机。
- **第一版就加二维码**：见上，没有对应的验证动作。

### 3. 时机

**推荐：任何时候都可以生成，但按本场状态给出不同的标签。**

- `drawLog` 中没有 `type === 'draw'` 记录：正常卡，标签“开抽前”。
- 已经有抽奖记录：仍可生成，但卡片顶部和 PNG 页脚都加红字“本场已抽 N 轮，此卡不是开抽前凭证”。
- 点击生成时，如果 `lottery-status.ts` 的 `phase` 不是空闲状态（正在抽奖），按钮不可用，避免在演出过程中弹浮层。

指纹本身在第一次抽奖开始前已经由 `lottery-controller.ts:119` 锁定，所以不存在“第一轮抽完才有指纹”的情况；风险在于主持人没有在开抽前展示卡片。

放弃的方案：
- **有抽奖记录后禁止生成**：主持人忘了开抽前出卡，活动后连存档用的卡都出不了，反而逼人去手工抄。
- **第一次点“开始”时强制弹卡片、必须确认**：改变抽奖主流程，违反“开始键直接进入流程”的现有节奏，也容易在现场造成卡顿。是否加一次性提示见待决问题 2。

### 4. 验证方如何核对

**推荐：**

1. 拿到卡片（现场拍照、PNG、纸质）的人，活动结束后向主持人要验证文件。
2. 在面板点“验证文件”导入。**新增**：结果区同时显示文件里的 `seedCommit`（按卡片同样的 8 位分组），而不是只说“通过”。
3. **新增**：结果区加一个“核对卡片指纹”输入框，输入卡片上的指纹（忽略空格和大小写），面板立即显示“与验证文件一致”或“不一致”，并指出第一个不同的分组。
4. 卡片上的核对说明与上面两步对应。

注意这个流程能证明的和不能证明的：能证明验证文件内部自洽，并且文件里的指纹等于卡片上的指纹；不能证明卡片是开抽前公布的，也不能证明卡片没被换。

放弃的方案：
- **只靠肉眼比对**：现状，64 位串容易看错。
- **扫码核对**：需要摄像头 API（非安全上下文可能没有）和二维码解码库，成本高于输入框。

## 二、外部随机性

### 5. 现场观众提供随机输入

**推荐：允许，作为可选步骤，放在随机算法升级之后（路线 B 的最后一步），先承诺、后输入、再混合。**

为什么有价值：主持人在公布指纹前，可以离线反复换种子，直到“想要的人”中奖再公布（名单是公开的，复算很便宜）。观众的输入是在指纹公布之后才产生的，主持人在公布时无法预知最终种子，也就没法挑。

流程：

1. 主持人侧生成 256 位随机数 `H`（见第 7 问），计算承诺指纹并在公证卡上公布。承诺的是 `H`，不是最终种子。
2. 公证卡公布后，现场收集一段观众输入 `A`：例如几个人各掷一次骰子读出的数字、某张彩票尾号、随手敲的一串字符，由主持人输入到一个文本框。输入前先做 Unicode NFC 规范化、去首尾空白，限制长度（例如 200 字符）。
3. 最终种子 `S = SHA-256("lottery-3d-final-seed-v3" ‖ H ‖ A 的字节长度 ‖ A)`，具体拼接格式在实现时写成固定规范并带版本号。
4. 验证文件新增 `audienceInput`（字符串）；`H` 作为 `seed`，验证器重新计算 `S` 并用 `S` 驱动随机流。没有 `audienceInput` 字段或为空串，表示没有混入外部输入，`S = H` 的派生规则也要在规范里写明。

离线下可行：只要一个文本框和一次 SHA-256，没有网络。

诚实的局限：
- 主持人拿到 `A` 之后立刻知道 `S` 和全部结果，如果不满意可以放弃、重新生成 `H` 和新指纹。程序无法阻止，只能靠流程：每次生成的指纹都要现场公布并记录，出现第二个指纹就要解释。
- `A` 由主持人录入，无法证明它真的来自观众。
- 没有输入就等于没有这一层保护，卡片要写明“本场未混入现场随机数”。

放弃的方案：
- **用观众输入直接当种子**：少数人可以挑选，且几个字符的熵很低。
- **在线随机信标（如公共随机数服务）**：违反离线硬约束。
- **先收集输入、再生成并公布指纹**：次序反了，主持人看过输入后仍然可以挑 `H`。

## 三、随机状态升级

### 6. 32 位状态的实际风险（量级估算）

下面的估算全部来自对代码的阅读和算术，没有跑任何攻击程序。

**1）需要哪些公开信息。**名单顺序和每轮抽取前的奖池是公开的（验证文件里有，现场也看得到）；每个中奖人在奖池中的位置，等价于 `nextInt` 的返回值。`nextInt(0, n-1)` 是 `floor(r × n)`，每个中奖人至少泄露约 `log2(n)` 比特（n 为当时奖池人数）。种子一共 32 比特，所以大致需要 `32 / log2(n)` 个中奖人，再多几个确认：奖池 300 人时约 4 到 5 个，奖池 30 人时约 7 个。这是信息量估算，不是实测。一个十人的奖项抽完，通常就够了。

**2）计算量。**候选种子 2^32 ≈ 4.3 × 10^9 个。每个候选只需推几步 mulberry32 并比对，每个候选的耗时我没有实测，按几十到一百纳秒的量级估：单核几分钟到十几分钟，多核或用更快的实现只会更短。作为对照，计划 008 记录的 SHA-256 是单线程每秒约 152 万次，穷举 2^32 约 `4.3×10^9 / 1.52×10^6 ≈ 2,800 秒`（约 47 分钟，单线程）；mulberry32 每个候选的开销预计远小于一次 SHA-256（未实测对比）。结论：**活动中途，靠公开的前几轮结果推出随机状态，在普通电脑上不需要特殊硬件。**

**3）更直接的泄露。**这里有几条不需要任何计算的路径：
- 第 15 行 `a = (a + 0x6d2b79f5) | 0` 说明状态只是一个计数器：每取一个数加固定常数，输出只由当前状态决定。所以验证文件里任何一个 `rngState` 或 `rngStateBefore`，都等于“从这里往后的全部随机序列”。
- `createVerificationPackage`（`lottery-fairness.ts:73、85`）把 `seed` 和 `finalState.rngState` 写进文件；面板的“复制验证数据”“下载验证文件”（`LotteryFairness.tsx:45-68`）在活动中途也能点；面板还一直显示“当前种子”（`LotteryFairness.tsx:106`）。任何一个人在活动中途看到、拍到、拿到这些，就能直接算出后面每一轮。
- 计划 008 的加盐承诺只堵住了“从指纹反推种子”，对以上两条没有作用。

**4）实际风险等级。**对“没有恶意参与者的内部抽奖”不严重。对“有人想预测后面的奖项”的场合，上面的 1) 和 3) 都可行。是否值得升级见待决问题 1。

### 7. 升级方案

**推荐：`sha256-ctr-v1`，256 位种子，用 SHA-256 计数器模式派生随机数。**

规则：
- 种子 `seedHex`：32 字节，`crypto.getRandomValues` 生成，64 位十六进制字符串（保存为字符串，不能用 number）。
- 随机流：第 `i` 个 32 字节块 `block_i = SHA-256("lottery-3d-rng-v1" ‖ seed 字节 ‖ i 的 8 字节大端)`，每块切成 8 个 uint32 字。
- `nextInt(min, max)`：从字流取 uint32，做拒绝采样（丢弃落在不能整除区间的值），不用浮点乘法，避免取模偏差和浮点边界问题。
- **`rngState`、`rngStateBefore` 变成“已消耗的字数”**，一个安全整数（≥ 0），不再是 uint32 内部状态。它是公开的、单调递增的计数器，暴露它不会泄露种子，也预测不了后面的值。撤销不回退这个计数（和现有规则一致，被撤销的轮次保留在流水里）。
- 算法标识：验证文件 `algorithm: 'sha256-ctr-v1'`，包 `version: 3`。承诺消息 `lottery-3d-commitment-v3:` + `seedHex` + `:` + `commitmentContext(...)`，`commitmentAlgorithm: 'sha256-committed-v3'`。256 位随机种子本身不可穷举，盐不再必要，省掉 `seedSalt` 字段（见待决问题 3）。
- 抽奖仍然是同步函数，所以需要同步的 SHA-256 实现。

两个同步 SHA-256 来源（只做调研，不安装）：

| 选项 | 说明 |
|---|---|
| `@noble/hashes` | 2.4.0，MIT，解包体积 691,646 字节（含全部算法，只引 `sha256` 经 tree-shaking 后会小很多，未实测），最近更新 2026-08-27；来源 `npm view @noble/hashes version license dist.unpackedSize time.modified` |
| 项目内自写约 60 行 SHA-256 | 无新依赖，但公平验证工具里自写密码学代码风险更高，必须用官方测试向量（FIPS 180-4 / NIST 示例）加测试 |

推荐 `@noble/hashes`，放弃自写。理由：公平验证的核心不该用没有经过外部审阅的哈希实现，体积代价可以用 tree-shaking 控制；这个选择留在待决问题 4，因为涉及新增依赖。

放弃的方案：
- **128 位状态的非密码学生成器（xoshiro128\*\*、sfc32 之类）**：把 2^32 的穷举空间扩到 2^128，但状态仍然等于“从这里往后的全部序列”，暴露 `rngState` 依旧等于公布未来；它们也不是为抗预测设计的（本文没有逐个核实具体算法的可恢复性，不下结论）。只解决了位数，没有解决结构。
- **每轮用 `crypto.subtle.digest` 派生**：`digest` 是异步的，要把同步的 `getRandomCard` 改成异步，波及抽奖流程；内网 HTTP 下 `crypto.subtle` 还不存在。
- **抽奖时直接调用 `crypto.getRandomValues`**：不可复算，违反“跳过和重放只使用已保存结果、整场可复算”的规则。
- **把 `rngState` 继续放大成 128 位内部状态并公开**：同样是公开状态等于公开未来。

连带要处理的泄露点：升级后，`seedHex` 在活动中途仍然不能出现在屏幕和导出文件里。推荐：v3 场次下“当前种子”区默认隐藏，加“揭示种子”按钮（活动结束后用）；活动中途导出的验证文件可以不带 `seedHex`（标记为“未揭示”，验证器只检查流水一致性，不复算随机流）。这是路线 B 里额外的范围，见待决问题 5。

### 8. 兼容

**推荐：算法注册表，旧算法冻结，升级只对新场次生效，旧数据永不原地转换。**

- 新增注册表：`algorithm 标识 → { 创建随机流, 校验 rngState 格式 }`。`mulberry32-v1` 的代码一个字不改，先补“黄金向量”测试：把当前实现对若干固定种子的输出序列和 `getState()` 序列固化成断言，防止重构时悄悄改变。
- 存档新增 `rngAlgorithm` 字段。**没有该字段的旧存档一律按 `mulberry32-v1` 恢复**，`seed` 仍是 number、`rngState` 仍按 uint32 校验。v3 场次用 `seedHex` 字符串字段，不复用 `seed`，避免 `number | string` 联合类型扩散。
- `config-restore.ts:75、87` 的 uint32 校验改成按 `rngAlgorithm` 选择校验函数。
- 验证文件按 `algorithm` 分派复算：`mulberry32-v1` 的 `version 1`、`version 2` 文件继续用原来的路径；`version 3` 走新路径。旧版本应用打开 v3 文件会得到“验证文件格式无效或版本不受支持”，这是预期，要在 README 现场准备里提一句“导出和验证请使用同一版本”。
- 什么叫“新场次”：没有存档时的首次创建、清空进度后。恢复出来的 v1 存档在整场活动中保持 v1，即使活动中途 PWA 更新了应用也不变。
- 彩排：用新算法，不读写正式进度，不影响上面任何一条。
- 回归测试必须包括：用基线 `c3f9290` 导出的 `version 1`（SHA-256、FNV-1a）和 `version 2` 验证文件各一份作为固定夹具，新代码仍然验证通过；旧存档夹具恢复后继续抽奖，结果与固化的黄金向量一致。

放弃的方案：
- **把旧存档在恢复时转换成新算法**：已抽出的结果无法由新算法复算，等于破坏已有记录。
- **直接替换 `mulberry32-v1` 的实现**：违反 AGENTS.md “改动算法前必须确认旧存档和旧验证文件仍能恢复和验证”。
- **用 feature flag 让主持人选算法**：增加现场配置项，且选错了没有人能发现。

## 风险

| 风险 | 缓解 |
|---|---|
| 主持人忘了开抽前展示卡片 | 卡片按状态打标签（第 3 问）；是否加一次性提醒见待决问题 2 |
| 卡片被误当成“已证明公布时间” | 卡片和面板都写明“本机时间，不能作为公布时间的证明”；保留面板原有提醒 |
| 无盐旧存档或 FNV 指纹出卡造成误解 | 三种状态分别处理（第 1 问） |
| 修改名单或奖项后旧卡失效 | 卡片写明“修改名单或奖项会生成新指纹”；按现有 `configHash` 机制，名单或奖项变化会清空进度，新场次新指纹 |
| v3 引入同步 SHA-256 实现，实现错误会静默改变抽奖结果 | 官方测试向量；验证文件由独立路径复算；黄金向量 |
| 旧版本应用无法打开 v3 验证文件 | 文档说明；不改动旧版本 |
| 观众输入可被主持人事后放弃重来 | 程序上无解，靠流程：每个指纹都公布并记录 |
| 两条路线都改 `LotteryFairness.tsx` 导致冲突 | 路线 A 的卡片放新文件，面板只加按钮；路线 B 的面板改动单独一个提交 |

## 正式实现的拆分建议

每个提交带自己的测试，一项一提交。路线 A 和路线 B 互相不依赖，可以由不同人并行做；路线 B 单独立项，因为它会改变验证文件格式。改动 UI 或流程的提交 push 前跑 `pnpm e2e`。

### 路线 A：公证卡

1. `feat: 公证卡数据与状态判定`：纯函数 `buildAttestation()`，输入当前场次，输出卡片字段、指纹分组、三种状态和“已抽 N 轮”标签；不含界面。单元测试覆盖三种指纹状态、已抽/未抽、指纹分组格式。验证：`pnpm exec vitest run <新测试文件>`。
2. `feat: 公证卡全屏浮层与打印样式`：面板加“公证卡”按钮，浮层用 React 文本渲染，`@media print` 样式。验证：组件测试加 e2e（打开浮层、指纹分组与面板一致、有抽奖记录时显示红字）。
3. `feat: 公证卡导出 PNG`：复用 `poster.ts` 的 canvas 思路，只画文字。验证：单元测试检查输出非空；浏览器手工看一次排版。
4. `feat: 导入验证文件时显示并核对指纹`：结果区显示文件指纹，增加核对输入框。验证：单元测试（空格、大小写、不一致位置）加 e2e。

路线 A 不需要任何新依赖。二维码若要做，作为第 5 个提交单独立项。

### 路线 B：随机状态升级（先单独评审再动手）

1. `test: 固化 mulberry32-v1 黄金向量和旧验证文件夹具`：不改行为，只加测试和夹具。
2. `refactor: 引入随机算法注册表`：`mulberry32-v1` 经注册表调用，所有现有测试照常通过，存档新增可选 `rngAlgorithm`，缺省按 v1。
3. `feat: sha256-ctr-v1 随机流`：同步 SHA-256、拒绝采样、`nextInt`；SHA-256 官方测试向量加分布测试；不接入任何场次。
4. `feat: 验证文件 version 3 与校验器`：新 `validPackage` 分支、新承诺消息、分派复算；旧夹具必须全部通过；篡改 `seedHex`、计数器、流水都要失败。
5. `feat: 新场次默认使用 sha256-ctr-v1`：新场次切换、存档保存和恢复；旧存档夹具恢复后仍是 v1。验证：单元测试加 e2e 加一次手工“用旧版本存档升级后继续抽奖”。
6. `feat: 隐藏当前种子，揭示后才可导出完整文件`（取决于待决问题 5）。
7. `feat: 现场随机数输入`（取决于待决问题 6，在第 4 条上加 `audienceInput`）。

## 测试计划汇总

- 单元：公证卡数据、指纹分组和核对、黄金向量、旧验证文件夹具、SHA-256 官方测试向量、v3 验证器的篡改用例。
- e2e：卡片浮层与面板指纹一致、已抽后的红字标签、导入文件后的核对输入框、新场次使用 v3 且旧存档仍是 v1。只覆盖 Chromium。
- 人工：Firefox 和 Safari 的打印预览；内网 HTTP 下 FNV 模式卡片置灰；现场投屏的字号和投影对比度。
- GitHub Actions 没有改动。

## 留给维护者决定的问题

1. 要不要做随机状态升级（路线 B）？风险等级见第 6 问；如果现场都是内部抽奖、没有人会拿到中途的验证数据，可以只做路线 A，并把面板里的“种子公开后后续结果可预测”提示改得更醒目。
2. 开抽前要不要加一次性提醒（第一次点“开始”时，如果本场没打开过公证卡，弹一条不阻塞的提示）？这需要记录“是否展示过卡片”，要不要进存档？
3. v3 是否去掉 `seedSalt` 字段（推荐去掉，256 位种子不可穷举）？保留的好处是承诺格式与 v2 一致。
4. 同步 SHA-256 用 `@noble/hashes`（新增依赖）还是项目内自写？推荐前者。
5. v3 场次是否隐藏“当前种子”，活动中途导出的验证文件是否不带种子？这会改变面板和导出行为，范围比单纯换算法大。
6. 是否需要“现场随机数输入”（第 5 问）？如果主持人的可信度本来就不是问题，可以不做。
7. 公证卡上是否需要显示二维码？如果要，是否接受 `uqr` 0.x 版本号的 API 稳定性风险？
8. 彩排卡片的水印文案和 PNG 是否允许彩排时导出？
9. 计划 013（工号）合入后，卡片是否需要显示“名单含工号”的标记？推荐写在文案里，不单独加字段。
